# Omico 契约驱动开发规范

**规范版本：** 1.0.0

**语言：** zh-Hans

**状态：** 草案

本规范定义 Omico Contract-Driven Development（OCDD）。OCDD 依赖 SDD 和 TDD；本规范规定其项目文档、契约边界、变更顺序、接受条件和一致性验证要求。

## 1. 规范状态与范围

本规范当前处于草案阶段。草案可在保持相同规范版本号的情况下修订，不得作为正式的合规声明依据。规范发布后，采用方必须满足所有适用要求，方可声明符合本规范。

本规范约束以下内容：

- 契约、一致性验证与实现之间的关系；
- OCDD 项目文档的路径、结构和规范性归属；
- 契约的评审、接受、变更和版本管理；
- 实现符合契约时所需的验证覆盖与证据。

本规范不限定产品类型、编程语言、构建系统、测试框架、交付平台或具体实现方式。

### 1.1 与 SDD 和 TDD 的关系

本规范中的 SDD 指 Specification-Driven Development，TDD 指 Test-Driven Development。本节说明 OCDD 对 SDD 和 TDD 的依赖，不引入独立于本规范其他章节的合规条件。

OCDD 从 SDD 引入规范先于实现并驱动实现的主线，以契约建立规范性来源。OCDD 进一步规定契约单元边界、接受顺序、不可变修订、版本管理和验证证据。采用其他 SDD 流程不表示自动符合 OCDD。

OCDD 从 TDD 引入验证先于实现的反馈循环。契约被接受后，采用方必须先从契约要求导出能够在要求不满足时失败的测试或其他一致性检查，再形成并重构实现。采用方可以使用红灯、绿灯、重构循环，但本规范不限定测试框架、测试层级或验证工具。测试在该过程中承担验证和反馈职责，不是契约语义的规范性来源。

OCDD 将 SDD 与 TDD 的主线连接为：接受契约，从契约导出测试或其他一致性验证，形成并重构实现，取得验证证据，接受实现结果。预期产品行为发生变化时，采用方必须先更新并接受契约，再更新测试和实现。只修复实现缺陷或重构内部结构时，契约语义必须保持不变。

## 2. 合规用语与术语

### 2.1 合规用语

本规范使用下列词语表达要求强度：

| 用语 | 含义 |
| --- | --- |
| 必须 | 为符合本规范而必须满足的要求 |
| 不得 | 为符合本规范而必须避免的行为 |
| 应当 | 推荐满足；偏离时应有明确理由 |
| 可以 | 可选行为 |

### 2.2 术语

| 术语 | 定义 |
| --- | --- |
| 采用方 | 声明采用 OCDD 并维护 OCDD 项目文档的组织或项目 |
| 契约使用方 | 依赖契约来设计、实现、验证或集成产品的参与方 |
| 契约 | 对产品可观察行为、边界、约束和兼容性的规范性定义 |
| 契约单元 | 具有稳定标识符和独立接受边界的一组契约要求 |
| 项目契约版本 | 标识一组契约定义的版本号 |
| 项目修订 | 在同一项目契约版本内，由不可变标识唯一确定的一组 OCDD 项目文档快照 |
| 规范性来源 | 对契约语义具有最终解释权的内容 |
| 实现结果 | 根据契约产生的代码、配置、构建产物或运行行为 |
| 适用条件 | 决定某项契约要求是否必须验证的环境、输入、能力或前置条件 |
| 一致性验证 | 判断实现结果是否满足契约要求的活动 |
| 验证证据 | 可追溯到契约标识符、项目契约版本和项目修订的事实、输出或材料 |
| 接受决定 | 由有权参与方对指定对象作出的可追溯认可 |

## 3. 契约模型

### 3.1 文档集合边界

采用方必须在项目入口文档中声明采用的 OCDD 规范版本和当前项目契约版本。

一个 OCDD 文档集合的边界由项目级契约和入口索引列出的全部契约单元共同确定。采用方可以分别建立多个 OCDD 文档集合，但每个集合必须具有独立且完整的入口文档。

### 3.2 规范性归属

项目入口文档中的项目级契约是跨契约单元规则的规范性来源。契约单元文档是其所声明行为和边界的规范性来源。

同一要求只能具有一个规范性来源。其他文档可以引用或解释规范性要求，但必须指向其唯一的规范性来源，且不得改变原要求的含义。

当非规范性说明与规范性来源不一致时，以规范性来源为准。

### 3.3 契约标识与契约单元边界

项目级契约和每个契约单元必须分别具有在当前 OCDD 文档集合内唯一且稳定的契约标识符。项目级契约的标识符必须由项目入口文档声明。

项目级契约和每个契约单元必须使每项要求能够被独立定位。每个契约单元还必须形成可以独立评审和接受的边界。

契约标识符一经用于已接受的项目契约版本，不得被重新分配给语义不同的项目级契约或契约单元。

### 3.4 契约优先

采用方必须先定义并接受契约，再依据已接受的契约设计一致性验证和实现。

契约接受决定必须至少标识：

- 契约标识符；
- 项目契约版本；
- 不可变的项目修订；
- 作出决定的参与方；
- 决定时间。

构建脚本、验证代码、生成器、运行输出和实现代码本身不是契约的规范性来源。只有当规范性文档明确纳入其中的内容时，被纳入的内容才具有相应的规范性效力。

## 4. OCDD 项目文档

### 4.1 文档语言与路径

OCDD 项目文档必须位于：

```text
docs/ocdd/<language>/
```

`<language>` 应使用 BCP 47 语言标签。每个 OCDD 文档集合必须选定一种规范性语言。其他语言的译文必须明确标记为非规范性，并链接到规范性版本。

规范性语言目录必须至少包含：

```text
docs/ocdd/<language>/
├── README.md
└── <scope>/
    └── <identifier-path>.md
```

除项目级契约外，每个契约单元必须归入一个 `<scope>`。`<scope>` 必须是规范性语言目录的直接子目录，并表示为一个以 ASCII 字母或数字开头和结尾、中间只包含 ASCII 字母、数字、下划线或连字符的片段。`<scope>` 用于分类契约，不属于契约标识符。

契约标识符必须由一个或多个以英文句点分隔的 ASCII 片段组成。每个片段必须以 ASCII 字母或数字开头和结尾，中间只能包含 ASCII 字母、数字、下划线或连字符。同一 OCDD 文档集合内的标识符按不区分 ASCII 字母大小写的方式判断唯一性。

契约单元的 `<identifier-path>` 必须将其契约标识符中的每个片段映射为一个路径片段，并以最后一个片段作为 Markdown 文件名。契约单元文档必须位于：

```text
docs/ocdd/<language>/<scope>/<identifier-path>.md
```

文件路径中的 `<identifier-path>` 必须能够还原出文档声明的完整契约标识符。

### 4.2 项目入口文档

`README.md` 必须采用下列结构：

```markdown
# <项目名称> OCDD 契约

**项目契约版本：** <version>

**项目级契约标识符：** `<project-contract-id>`

**采用规范：** OCDD <spec-version>

## 项目级契约

<适用于全部契约单元的规范性规则>

## 契约索引

- [`<contract-id>`](<scope>/<identifier-path>.md)：<契约单元名称>
```

项目入口文档必须列出当前 OCDD 文档集合内的全部契约单元。未被索引的文档不得作为该集合的契约单元。

项目级契约必须定义全部适用的跨契约单元规则；没有适用规则时必须明确声明。

`<project-contract-id>` 必须遵循第 4.1 节的契约标识符语法和唯一性规则。它只标识该入口文档定义的项目级契约，不映射为 `<identifier-path>`。

项目入口文档是项目级契约的规范性来源。项目级契约继承入口文档声明的项目契约版本。

### 4.3 API 契约文档

声明 API 行为的契约单元必须位于：

```text
docs/ocdd/<language>/api/<identifier-path>.md
```

API 契约文档必须采用下列结构：

```markdown
# `<contract-id>`：<契约单元名称>

- 依赖契约： <contract-references>
- 非规范性外部参照： <external-references>

## 规范性定义

## 可观察行为

## 边界与错误

## 兼容性

## 验证要求
```

“依赖契约”和“非规范性外部参照”字段在没有适用内容时可以省略。

一个 API 契约文档必须只定义一个契约单元。其文件路径和标题中的契约标识符必须一致。

采用方可以定义其他契约类别。其他类别必须遵循本规范对契约单元、规范性归属、内容、接受和验证的通用要求。

## 5. 契约内容

### 5.1 必备内容

项目级契约必须定义：

1. 稳定且唯一的契约标识符；
2. 每项跨契约单元规则的适用条件和判定要求；
3. 所定义的项目级可观察行为和约束的兼容性承诺。

每个契约单元必须定义：

1. 稳定且唯一的契约标识符；
2. 对外可观察的行为；
3. 输入、输出、状态或交互边界；
4. 错误、失败或拒绝行为；
5. 兼容性承诺；
6. 一致性验证所需的适用条件和判定要求。

不适用于项目级契约或某个契约单元的内容必须明确声明不适用及其理由。

### 5.2 可观察行为与边界

契约要求必须以契约使用方能够观察或验证的结果表达。契约可以描述实现约束，但只有当该约束是产品要求、互操作要求、安全边界或兼容性承诺的一部分时，才能作为规范性要求。

边界条件必须覆盖适用的有效输入、无效输入、极限值、缺失值、重复操作、状态转换、并发行为、失败恢复和资源限制。

契约中的规范性示例必须说明其覆盖的要求。示例、说明、验证证据和接受决定不得隐式扩展或缩小契约要求。

### 5.3 契约依赖与外部引用

“依赖契约”用于列出本契约直接使用的其他契约单元。每项依赖必须解析到同一不可变项目修订中的契约标识符。依赖引用只建立可追溯关系，不复制被引用契约的要求，不改变规范性归属，也不表示被引用契约已经接受；本契约实际使用的定义或要求必须在正文中明确引用。

契约可以引用外部规范。规范性引用必须固定到可唯一识别且可获得的版本或修订，并明确说明被纳入的范围。

外部规范发生变化时，除非契约明确采用新的版本或修订，否则不得自动改变当前契约的含义。

“非规范性外部参照”只提供理解或实现背景，不纳入契约语义，也不得替代契约的规范性定义、边界或验证要求。非规范性外部参照与契约不一致时，以契约为准。

非规范性外部参照可以包括产品需求、议题、决策记录或其他上游材料。上游材料中的义务必须在项目级契约或契约单元中定义，才具有 OCDD 契约语义。本规范不要求采用方创建或引用上游需求，不规定其形式、位置、生命周期、评审或接受方式，也不将其纳入 OCDD 合规范围。

## 6. 变更与接受

### 6.1 契约变更

对于尚未发生首次接受的项目契约版本，采用方可以在保持版本号不变的情况下修订契约，但每个接受候选必须对应一个不可变的项目修订。

项目契约版本一经接受，对应的项目修订必须保持不变。后续规范性语义变化必须按照第 8 节声明新的项目契约版本；不改变任何规范性含义的编辑性修正也必须递增 `PATCH`，并形成新的项目契约版本和不可变项目修订。

预期产品行为变化时，采用方必须先更新受影响的项目级契约和契约单元。契约不得通过实现或验证结果反向推导出未声明的产品行为。

### 6.2 接受顺序

采用方必须按以下顺序完成开发活动：

1. 定义、评审并接受项目级契约和入口索引列出的全部契约单元；
2. 从已接受的契约导出一致性验证，使每项契约要求至少对应一个能在要求不满足时失败的检查；
3. 根据同一项目契约版本和项目修订进行实现；
4. 在全部适用条件下执行一致性验证并取得验证证据；
5. 根据验证证据判断实现是否满足契约；
6. 由有权参与方接受实现结果。

上述活动必须可追溯到同一组契约标识符、项目契约版本和不可变项目修订。

项目级契约和入口索引列出的全部契约单元的接受决定必须指向包含这些契约的同一不可变项目修订。实现接受决定必须指向该项目修订，标识被接受实现结果或构建产物的不可变版本，并关联用于判定的验证证据。

### 6.3 不一致处理

当实现结果与契约不一致时，采用方必须先判断差异属于实现缺陷还是契约变更：

- 实现缺陷必须通过修改实现或验证来解决，契约语义保持不变；
- 契约变更必须先修改并接受契约，在适用时声明新的项目契约版本，然后重新执行第 6.2 节规定的活动。

现有实现行为不得作为跳过契约或接受步骤的理由，也不得自动成为未声明契约变更的依据。

## 7. 一致性验证

### 7.1 要求覆盖

采用方必须能够从每项契约要求定位至少一个在要求不满足时会失败的检查，也必须能够从每个规范性检查定位其验证的契约要求。

定位关系可以通过契约标识符、要求位置、检查名称、检查元数据、验证输出或采用方定义的稳定约定建立。本规范不要求维护独立的追溯文档或映射表。仅将检查放在同一文件、测试套件或构建任务中，不足以证明定位关系；采用的方式必须能够区分具体要求和检查。

验证必须优先检查外部可观察行为。内部结构、私有接口或实现细节检查只能作为补充，除非相应实现约束本身属于规范性契约要求。

### 7.2 适用条件与验证方法

采用方必须识别影响契约行为的适用条件类别，并验证每个适用类别。验证方法可以包括边界值、等价类、性质检查、状态转换、故障注入或具有代表性的场景。

随机抽样只能作为补充方法。若采用方无法证明抽样覆盖全部规范性要求和适用条件，抽样结果不得替代确定性验证。

### 7.3 验证证据

验证证据必须足以判断每项适用契约要求是否满足，并至少关联：

- 契约标识符和要求位置；
- 项目契约版本和不可变项目修订；
- 验证条件和验证方法；
- 实现结果或构建产物的不可变标识；
- 验证结果和取得时间。

不同工具或环境产生的证据可以合并使用，但采用方必须能够说明这些结果对应同一契约要求和等价的适用条件。未在契约中声明的输出不得被解释为新的规范性行为。

验证证据的载体、位置和保留期限由采用方的契约或治理规则确定。本规范不要求为验证证据建立特定的 OCDD 项目文档。

当某项契约要求无法直接验证时，契约必须声明可接受的替代验证方法、适用限制和判定标准。

## 8. 版本与修订

### 8.1 版本号

OCDD 规范版本和项目契约版本必须采用语义化版本格式 `MAJOR.MINOR.PATCH`。

| 变更类型 | 版本变化 |
| --- | --- |
| 破坏既有规范性语义或兼容性承诺 | 递增 `MAJOR` |
| 以向后兼容方式新增规范性能力或要求 | 递增 `MINOR` |
| 不改变既有规范性语义的修正或澄清 | 递增 `PATCH` |
| 不改变规范性语义的规范状态转换 | 递增 `PATCH` |

### 8.2 修订与不可变性

OCDD 规范在发布前可以保持相同版本号进行草案修订。规范一经发布，对应该版本号的内容必须保持不可变；任何后续规范性变化必须产生新的规范版本。

项目契约版本在首次接受前可以保持相同版本号进行修订，但每个接受候选必须通过提交标识、内容摘要或其他不可变标识唯一确定。

当有权参与方在同一不可变项目修订上接受项目级契约和入口索引列出的全部契约单元时，该项目契约版本视为已接受。对应快照必须保持不可变。后续规范性语义变化必须产生新的项目契约版本，并保留既有已接受修订的可追溯性。

当前 OCDD 项目文档可以只呈现当前项目契约版本，但采用方必须能够取得其所依赖的既有已接受修订。

### 8.3 兼容性

契约必须从契约使用方的角度定义兼容性。兼容性判断必须考虑适用的输入、输出、错误、状态转换、时序、资源约束和互操作行为。

仅保持源代码可编译、接口名称不变或验证通过，不足以单独证明契约兼容。

### 8.4 OCDD 规范状态

OCDD 规范可以处于以下状态之一：

- 草案：仍可修订，不得作为正式合规声明依据；
- 已发布：内容不可变，可以作为合规声明依据；
- 已废弃：不再推荐新采用，但既有采用方仍可依据对应的不可变规范内容进行判断。

规范状态必须在规范文档中直接声明。任何规范状态转换都必须由有权维护方作出决定，产生可唯一识别的不可变规范修订，并按照第 8.1 节产生新的规范版本。规范状态发生变化时不得沿用原规范版本号；即使不改变规范性语义，也必须至少递增 `PATCH`。

## 9. 采用方合规

规范发布后，采用方只有在满足以下全部条件时，才能声明符合本规范：

1. 项目入口文档完整声明 OCDD 规范版本和项目契约版本；
2. OCDD 项目文档符合第 4 节规定的路径和结构；
3. 项目级契约和契约单元具有稳定且唯一的标识符，并具有唯一规范性来源；
4. 项目级契约和契约单元满足第 5 节的适用内容要求；
5. 契约在实现接受前完成接受；
6. 一致性验证覆盖全部适用要求和条件，并产生充分的验证证据；
7. 契约、验证、实现和接受决定可追溯到同一项目契约版本、不可变项目修订和适用契约标识符；
8. 实现结果已由有权参与方接受，并满足全部适用契约要求；
9. 版本、修订和兼容性管理符合第 8 节的要求。
